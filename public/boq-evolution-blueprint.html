Template-Driven Lifecycle

Single BOQ vs 3-Tier Proposal: Current Bottlenecks vs Unified Scope Spine

In our current app, the Project Setup Wizard allows choosing between a Single Turnkey BOQ (Comfort Upgrade) or 3 Distinct Tiers (Essential, Comfort, Complete Harmony). While initial creation is instant, post-creation updating creates severe manual friction. Here is the architectural comparison.

1

Template & Item Bank

How typologies & items are declared.

Current Implementation

Flat arrays of item IDs mapped to room strings (living: ['gen-001']). Tiers use rough mathematical multipliers (materialMod: 0.88 vs 1.35).

❌ Flaw: Artificial multipliers hide actual subcontractor line items.
New Proposed Architecture

Parametric Smart Assemblies: Every bank item natively carries 3 concrete subcontractor trade specs (e.g. Commercial Ply vs Marine BWP vs HDHMR; 0.8mm vs 1.0mm Merino vs PU Paint; Standard vs Soft-Close vs Blum).

✓ Benefit: Grounded in real subcontractor line items with zero artificial multipliers.
2

Initial Generation

Wizard selection: Single vs 3-Tier Mode.

Current Implementation

Wizard stamps out 3 completely detached BoqItem[] arrays. The moment generation finishes, all 3 tiers sever connection to each other and to the template.

❌ Flaw: An isolated snapshot with no lasting spatial link.
New Proposed Architecture

The Unified Scope Spine: Rooms and line items exist on one master spatial backbone. Quantities bind to physical room dimensions. Switching between Single and 3-Tier mode is a non-destructive view toggle!

✓ Benefit: Convert between Single and 3 Tiers at any time with zero loss of data.
3

Post-Creation Editing

Designer customizes room items or dimensions.

Current Implementation

Designer edits Active Tier (e.g. Master Wardrobe from 45 to 63 sft). Tiers 1 and 3 remain at 45 sft. When presenting to the client, comparing tiers compares completely different scopes.

❌ Flaw: 3x manual data entry or painful desync.
New Proposed Architecture

Bi-Directional Spatial Propagation: Changing wardrobe quantity to 63 sft updates the spatial quantity across all 3 tiers automatically. Finish specifications and hardware remain tier-specific.

✓ Benefit: Edit once. All 3 proposal tiers remain mathematically synchronized.
4

Budget Revisions ("What-If")

Client demands: "Drop budget by ₹3.5 Lakhs".

Current Implementation

Manual guesswork. Designers either slash trade margins across items (risking zero-margin execution) or manually open 35 items across 3 tiers.

❌ Flaw: Takes 90–120 minutes per revision round. High margin erosion.
New Proposed Architecture

Inverse Budget Clamper (Algorithm 4): Drag the budget slider. The engine computes 3 clean trade-off paths: Finish Swaps, Scope Deferral, or Volume Margin Tuning, re-aligning all 3 tiers in 30 seconds.

✓ Benefit: Client revisions handled live on call without sacrificing studio gross margins.

How Do We Proceed? The 3 Concrete Engineering Options

To transition our software to the Studio Brain without disrupting ongoing client work, here are the 3 architectural pathways.

Option 1 (Recommended) Zero Risk

Non-Destructive Dual-Engine Architecture

Utilizes the existing architecture: 'legacy' | 'canonical' discriminator already in types.ts (line 1636).

How it works:

• All existing active projects remain locked to Engine v1 (Legacy Array Mode). Their data is 100% isolated and never touched.

• New projects (or existing drafts where the designer explicitly clicks "Upgrade to Studio Brain") run on Engine v2 (Unified Scope Spine + Studio Brain).

• Studio defines its trade policies in Studio Settings. AI auto-populates defaults from past Zoho records.

Data Integrity: 100% Safe (Zero Drift)
Migration Scripts: None Required
Time to Ship: Fast & Phased
Option 2 Low Risk

Schema-Compatible Shadow Spine (Decorator)

Retains the exact current schema (ProposalTier[] with detached BoqItem[]), but adds non-breaking metadata tags.

How it works:

• Injects optional spineKey?: string and assemblyRef?: string into BoqItem.

• The Studio Brain acts as an in-memory orchestrator: when a designer edits an item in Tier 2, the Brain updates Tiers 1 and 3 in memory before saving the standard array back to Firestore.

• All downstream modules (PDF, Material Selection, Bundles) continue reading standard arrays.

Data Integrity: Safe (Backward-Compatible)
Redundancy: Array Duplication Persists
Time to Ship: Moderate
Option 3 High Effort

Full Canonical Database Rewrite & Projection

Completely replaces ProposalTier[] in Firestore with a single ScopeSpine database collection.

How it works:

• Requires running an offline database migration script across all past Firestore projects.

• For backward compatibility with legacy views, an In-Memory Projection Adapter synthesizes virtual tiers: ProposalTier[] on-the-fly.

• High architectural purity, but introduces risk of discrepancy on older projects if migration scripts miss custom manual overrides.
